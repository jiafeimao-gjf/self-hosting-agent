# SPEC-022 流式输出

状态：**已实现**

## 为什么要它

在补齐之前，一轮对话是这样的：人类发一句话 → 界面**完全静止**几十秒（只有一个忙碌指示）→ 整段回答一次性出现。

真模型一轮动辄十几秒到几十秒，这种「静默然后砸一大段」的体验有两个问题：

1. **像卡死**：人类不知道它是在思考、在排队、还是已经挂了；
2. **看不出进展**：长回答只能等全部生成完才能读第一句。

流式输出把模型吐出来的字**实时**送到界面。这是 SPEC-018 里那个「体验缺口」的正解。

## 一、两个关键设计决定

### 1. 传「累积全文」，不传分片

增量回调收到的是**累积到现在的全文**（`"预算"` → `"预算还剩"` → `"预算还剩 62%"`），不是分片。

理由：分片是**有状态**的——丢一条、重一条、乱序一条，客户端拼出来的文本就是错的（而且很难发现）。
传全文则天然**幂等**：同一份内容重放多少次，界面上的结果都一样。代价是每条都带上前缀，
但节流后几十毫秒一条、一条几百字节，换来的是「不可能画出错文本」。

### 2. 增量是瞬态，不进事件日志

`agent.delta` 帧**只转发、不落日志**，这是对 KERN-009（每一帧都写进事件日志）的一处**明确豁免**：

一次回答可能产生几十上百条增量，逐条记账会把事件日志彻底淹没——而它们提供的全部信息，
最终那条 `agent.thinking` 里一字不少地都有了。审计要的是事实，不是过程噪音。

接口侧靠**节流**把量压下来：适配器按时间（默认 120ms）合流，收尾那一条一定发出去
（否则界面会停在半句话上）。

## 二、协议与链路

```
模型 SSE ──▶ 适配器（解析 + 节流 + 累积全文）
              │ onDelta(累积全文)
              ▼
          Loop: emit({t:'agent.delta', agent, text})
              │
              ├─ 池子：转发但不落日志
              ▼
        SSE `frame` ──▶ 客户端：原地更新流式气泡
                          │
        最终 agent.thinking ──▶ 收掉气泡 + 渲染正式消息
```

- **OpenAI 兼容**：`stream: true`，`data:` 里取 `choices[0].delta.content`；
  工具调用在 `delta.tool_calls`（按 `index` 拼 `id` / `name` / `arguments`），收尾约定 `data: [DONE]`。
- **Anthropic**：`stream: true`，取 `content_block_delta.text_delta`；
  工具入参走 `input_json_delta.partial_json`，工具名在 `content_block_start`，收尾看 `message_delta.stop_reason`。
- 两条流都会**拼回各自的完整响应形状**，再交给与非流式完全相同的解析函数——
  这样「流式」与「非流式」不可能解析出两种结果。

## 三、降级

网关不认 `stream`、中途断流、流里夹 error —— 都不能把整轮搞死：

- 流式失败 → **退回非流式**重来一次（原因记进 `onStreamFallback` 回调，便于排障）；
- **超时除外**：再试一次只会让人类多等一个超时，直接上抛。

## 验收标准

- **STREAM-001** SSE 解析器：跨 chunk 切断、CRLF、多行 `data`、注释心跳、`[DONE]`、`flush()` 吐出最后一条；增量节流按时间合流且收尾必发。
- **STREAM-002** 两家适配器都能流式解析：OpenAI 的 `delta.content` + 分批 `tool_calls`、Anthropic 的 `text_delta` + `input_json_delta` + `content_block_start`；请求体带 `stream: true`；**拼回来之后与非流式解析结果完全一致**。
- **STREAM-003** 流式失败降级为非流式（并留下可查原因），而不是把整轮变成错误；超时不降级重试。
- **STREAM-004** Loop 把增量作为 `agent.delta` 帧外发（内容是累积全文），最终 `agent.thinking` 文本完整；**池子不把 `agent.delta` 写进事件日志**，其余帧照旧全记。
- **STREAM-005** 客户端：流式气泡**原地更新**（不 append）、文本一律 `textContent`/转义写入、最终消息到达时收掉气泡不重复、整体重建对话流时清掉气泡引用。
- **STREAM-006** 确定性演示模型（`--model demo`）也走流式，因此整条流式链路可以在没有网络的情况下被确定性测试。
